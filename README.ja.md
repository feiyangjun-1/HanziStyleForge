# HanziStyleForge

あるフォントのスタイルで、別のフォントの字形基準に従って漢字を全て生成し直します。

ターゲットフォントから筆画のスタイルを学習し、参照フォントの構造に従って、参照フォントが収録する漢字を一字ずつ描き直し、インストール可能な `.ttf` にまとめます。ターゲットフォントに既にある字も描き直すので、全体が統一されます。

主な用途は二つです。

- 字数の拡張。数千字しかないターゲットフォントを二万字以上に広げる
- 字形基準の変更。台湾（または日本、韓国）字形のターゲットフォントを、参照フォントを大陸版に差し替えるだけで大陸規範に描き直す。スタイルはそのまま

> 実験的なプロジェクトです。全体で数日から数週間かかり、いつでも中断・再開できます。

## 準備するもの

### 二つのフォント（必須）

| ファイル | 役割 |
|---|---|
| `fonts/target.ttf` | スタイル source。筆画がどう見えるかだけを学習します |
| `refs/ref.otf` | 構造 source。この字形に従って描き、生成する字の範囲もこれが決めます |

ファイル名の主幹で照合するため拡張子は問いません。`refs/ref.ttf` でも同様に動作します。

字形基準は `ref` が決めます。大陸規範なら大陸版を、台湾・香港・日本・韓国の基準ならそれぞれ対応するものを置いてください。どれが正しいかをプログラムは判断しません。

静的フォントのみ対応。可変フォント、TTC、OTC は非対応です。`target` は `glyf` テーブルを持つ TrueType、`ref` は TrueType でも CFF/OTF でも構いません。

### 同形字リスト（任意、品質に影響）

`data/same_form_han.txt`。リポジトリには含まれないので自分で用意します。二つのフォントが**同じ構造**で描く字（部品と配置が一致し、スタイルだけが異なる字）を列挙したものです。

このファイルがあると、`prepare` が一字ごとに「参照の構造 → ターゲットの字形」という学習サンプルを作ります。モデルが実際の参照フォントを入力として見る唯一の機会です。無い場合はターゲットの自己再構成だけになり、動作はしますが、生成時に実際に与えられる入力をモデルは学習中に一度も見ないことになります。

構造が異なる字を入れては**いけません**。それは地域字形を別の地域字形に変換するようモデルに教えることになり、参照フォントを使う目的と逆になります。

```bash
python tools/same_form_review.py
```

ウィンドウが開き、各字を両フォントで左右に並べて表示します。字形が同じなら `y`、異なるなら `n`。左右キーは判定せずに移動、`u` は現在の字の判定を取り消します。**キーを押すたびに即座にディスクへ書き込む**ので、ウィンドウを閉じても電源が落ちても失うのは押しかけの一打だけで、再度開くと最初の未判定の字から再開します。

`--only-undecided` は判定済みを飛ばし、`--sort suspicious` はトポロジーの食い違いが大きい順に並べるので、明らかに異なるものを先に片付けられます。

リストが既にあり進捗ファイルが無い場合は、その字を判定済みとして読み込み `.bak` を残すので、既存のリストを上書きせずに continue できます。

書式は [data/README.md](data/README.md) を参照してください。

## 動作環境

NVIDIA GPU が必須です。CUDA が無いと学習は動きません。

| 環境 | 学習 |
|---|---|
| Windows / Linux + NVIDIA | 可 |
| macOS | 不可。NVIDIA GPU が無く、Apple MPS は未対応 |
| 独立 GPU 無し | 不可 |

Python 3.10-3.14、空きディスク 150 GB 推奨。VRAM 12 GB で十分で、既定値はこれに合わせて調整済みです。

Mac でもインストール、セルフテスト、フォントの検査、生成済み画像のフォント化までは可能です。学習は NVIDIA カードのある機械で行ってください。

## 使い方

### Windows

| 手順 | ダブルクリック | 内容 |
|---|---|---|
| 1 | `install.bat` | 環境構築。一度だけ |
| 2 | — | フォントを `fonts\` と `refs\` へ |
| 3 | `verify.bat` | 確認 |
| 4 | `run.bat` | 実行 |

`stop.bat` で次のチェックポイントで安全に終了します。`run.bat` を再度実行すれば続きから走ります。

### Linux / macOS

```bash
./install.sh          # 環境構築
./verify.sh           # フォントを置いてから確認
./run.sh              # 実行。./stop.sh で一時停止
```

`Permission denied` と出たら先に `chmod +x *.sh` を実行してください。

## VRAM の設定

既定の `config.json` は 12 GB 向けに調整済みで、12 GB のカードなら変更不要です。以下は RTX 5070 Ti Laptop（11.9 GB）で実測した 1 ステップのピーク使用量です。

| 段階 | 既定 batch | ピーク VRAM |
|---|---|---|
| vq256 | 4 | 3.1 GB |
| vq384 | 2 | 3.4 GB |
| vq512 | 1 | 3.0 GB |
| direct256 | 6 | 4.6 GB |
| direct384 | 3 | 5.2 GB |
| latent256 | 6 | 5.4 GB |
| latent384 | 4 | 7.8 GB |
| latent512 | 4 | 11.2 GB |

### 推奨値

| VRAM | 変更内容 |
|---|---|
| 16 GB 以上 | 不要 |
| 12 GB | 不要 |
| 10 GB | `latent512` の `batch_size` を 4 から 2、`gradient_accumulation` を 1 から 2 |
| 8 GB | 上記に加えて `latent384` も 4 から 2 / 1 から 2 |
| 6 GB | 全段階で `batch_size` を半分、`gradient_accumulation` を倍 |

原則として `batch_size` と `gradient_accumulation` の積は変えないでください。変えると実効バッチが変わり、学習率が合わなくなります。

VRAM が多くても大きくは速くなりません。ボトルネックは計算であってメモリではなく、batch を 4 から 8 にしてもスループットの向上は 10% 未満でした。

## CPU の設定

`training.workers` はデータ読み込みプロセス数で、既定は 4 です。

| 物理コア | workers |
|---|---|
| 4 | 2 |
| 6-8 | 4（既定） |
| 12 以上 | 6-8 |

worker 1 つあたり約 1.5-2 GB のメモリを使います。メモリが厳しければ減らしてください。

`cpu_threads`、`interop_threads`、`opencv_threads` は増やさないでください。学習は GPU 律速なので、これらを増やすと CPU が GPU のスケジューリングを奪うだけです。

worker を増やすべきかの判断は、実行中のターミナルの batch/s を見ます。GPU 使用率（`nvidia-smi`）が 80% を下回り続けるなら効果があり、90% 以上なら計算律速なので増やしても変わりません。

## 設定の変更

設定はプロジェクト直下の `config.json` で、四つの起動スクリプトが渡すのはこれ一つです。保存は UTF-8 で行ってください。

各段階には `name` があるので、名前で探すのが確実です。8 GB のカードなら `fusion` → `diffusion` → `phases` の中の `"name": "latent512"` の項目を変更します。

```json
{
  "name": "latent512",
  "batch_size": 2,
  "gradient_accumulation": 2
}
```

積は 4 のままで変わりません。

### 進捗が無効になる変更

チェックポイントは指紋で照合します。一致しないとその段階の 1 エポック目からやり直しになります。

| 変更 | 結果 |
|---|---|
| `fusion.vq.phases[]` の任意の項目 | その VQ 段階を再学習 |
| `fusion.diffusion.phases[]` の任意の項目 | その拡散段階を再学習 |
| `fusion.style_encoder` の `size`、`epochs`、`batch_size`、`learning_rate`、`virtual_length`、`references_per_set`、`cell_grid`、`query_gain` | スタイル段階を再学習 |
| `fusion.refiner` の `size`、`epochs`、`batch_size`、`gradient_accumulation`、`learning_rate` | 精緻化段階を再学習 |
| `fusion.style_encoder.early_stopping` | 安全 |
| `fusion.refiner.minimum_epochs`、`minimum_relative_improvement` | 安全 |
| `training.workers`、`training.amp`、`checkpoint_every_steps`、`preview_every` | 安全 |
| `build` の任意の項目 | 安全。TTF 生成時にしか読まれません |

VQ と拡散の `early_stopping` は phase の内側にあるため、変更するとその段階が再学習になります。スタイル段階と精緻化段階とは異なる点です。

VRAM 関連の設定は実行前に決めてください。途中で変えるとその段階をやり直すことになります。

### VRAM 不足

エラーがどの段階で出たかを確認し（ターミナルに段階名が表示されます）、その段階だけを変更します。`batch_size` を半分、`gradient_accumulation` を倍、まだ足りなければもう一度。

### フォントが大きすぎる

サイズのほとんどは字形の輪郭です。制御するのは `build.curve_simplify` で、値が大きいほど残す点が減ります。参照フォントで複雑さの異なる 17 字を実測した結果です。

| `curve_simplify` | 点数/字 | Dice |
|---|---|---|
| 0.55 | 611 | 0.9848 |
| 1.2（既定） | 167 | 0.9843 |
| 1.8 | 130 | 0.9812 |
| 2.5 | 117 | 0.9786 |

手作業で設計されたフォントは 1 字あたり約 156 点なので、既定値はその水準です。二万字あまりで約 14 MB になります。1.8 を超えると一致度が明確に落ちます。0.55 まで下げても利点はなく、増えた点は字形ではなくラスターのジャギーをなぞっているだけです。

他のつまみは効果が弱く、`maximum_points_per_contour` を 480 から 96 に下げても 69% までしか減りませんでした。触る必要はありません。

サイズの内訳を見るには次を実行します。

```bash
python tools/font_size_report.py build/target-HanziStyleForge.ttf
```

### 変更の確認

```bash
verify.bat        # Linux/macOS: ./verify.sh
```

JSON の構文と値の範囲を確認します。JSON でよくある誤りはカンマの過不足で、最後の項目の後ろにカンマは置けません。

## 中断について

段階ごと、生成された字ごとにチェックポイントがあるので、同じコマンドをもう一度実行すれば途中から再開します。停電、ブルースクリーン、Ctrl+C いずれも同じです。起動スクリプトはエラー後に自動で再試行し、20 回連続で失敗して初めて停止します。

起動スクリプトを使わず自分でコマンドを打って再開する場合は注意が必要です。停止を要求するとプロジェクト直下に `STOP_AFTER_CHECKPOINT` というマーカーが残ります。起動スクリプトは毎回これを削除しますが、手打ちでは削除されないため、新しい実行が最初のチェックポイントで止まります。手動で再開する前に削除してください。

## よくある質問

**どのくらい時間がかかりますか。** 字数と GPU によりますが数日から数週間です。既定設定で 12 GB のノート PC 向け GPU なら週単位です。

**一部の字だけ生成できますか。** できます。`scope.mode` を `chars_file` にし、`scope.extra_chars_file` に字リスト（1 行に 1 字、または `U+4E00` 形式のコードポイント）を指定します。まず数百字で試すのがおすすめです。

**生成された字が規範から外れることはありますか。** 構造ゲートがあります。連結成分数と穴の数が参照字と合わない候補は却下され、参照字形が使われます。筆画が一本多い・少ないといった誤字は防げますが、一部の字が参照フォントの見た目のまま残る代償があります。

**漢字以外は変更されますか。** されません。ラテン文字、数字、約物、仮名、ハングル、および OpenType のレイアウトとヒンティングのデータは全て `target.ttf` からそのまま保持され、ビルド時にバイト単位で検証されます。

**`requires CUDA, but torch.cuda.is_available() is False` と出る** 使用可能な NVIDIA GPU が見つかりません。ドライバーを更新するか、CUDA 版 PyTorch が入っているか確認してください。

**`does not support training.device='mps'` と出る** Apple GPU は非対応です。

## 仕組み

```text
target.ttf（スタイル）  ref.otf（字形構造）
        └──────┬──────┘
               ↓
   スタイル符号化 → VQ 筆画コードブック → 潜在拡散 → 精緻化
               ↓
   多候補生成 → 構造ゲート → 品質検査 → ベクター化 → TTF
```

学習サンプルは二種類あります。ターゲットフォントの自己再構成と、同形字リストが対象とする「参照の構造 → ターゲットの字形」の対です。どちらも正解は `target.ttf` のみから取り、構造の入力は `target` 自身か `ref` のどちらかからのみ取ります。このデータフローは実行時に検証されます。
