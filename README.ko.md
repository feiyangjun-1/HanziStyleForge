# HanziStyleForge

한 폰트의 스타일로, 다른 폰트의 자형 기준을 따라 한자를 전부 다시 생성합니다.

타깃 폰트에서 획의 스타일을 학습하고, 참조 폰트의 구조에 따라 참조 폰트가 수록한 한자를 하나씩 다시 그린 뒤, 설치 가능한 `.ttf`로 묶습니다. 타깃 폰트에 이미 있는 글자도 다시 그리므로 전체가 통일됩니다.

주요 용도는 두 가지입니다.

- 글자 수 확장. 수천 자뿐인 타깃 폰트를 이만 자 이상으로 넓히기
- 자형 기준 변경. 대만(또는 일본, 한국) 자형인 타깃 폰트를, 참조 폰트를 대륙판으로 바꾸기만 하면 대륙 규범으로 다시 그림. 스타일은 유지

> 실험적 프로젝트입니다. 전체 실행에 며칠에서 몇 주가 걸리며, 언제든 중단하고 이어서 실행할 수 있습니다.

## 준비물

### 폰트 두 개 (필수)

| 파일 | 역할 |
|---|---|
| `fonts/target.ttf` | 스타일 출처. 획이 어떻게 생겼는지만 학습합니다 |
| `refs/ref.otf` | 구조 출처. 이 자형을 따라 그리며, 생성할 글자 범위도 이것이 정합니다 |

파일 이름의 어간으로 대조하므로 확장자는 상관없습니다. `refs/ref.ttf`도 동일하게 동작합니다.

자형 기준은 `ref`가 정합니다. 대륙 규범을 원하면 대륙판을, 대만·홍콩·일본·한국 기준을 원하면 해당하는 것을 두십시오. 어느 쪽이 더 옳은지 프로그램은 판단하지 않습니다.

정적 폰트만 지원하며 가변 폰트, TTC, OTC는 지원하지 않습니다. `target`은 `glyf` 테이블이 있는 TrueType이어야 하고, `ref`는 TrueType이나 CFF/OTF 모두 가능합니다.

### 동일 자형 목록 (선택, 품질에 영향)

`data/same_form_han.txt`. 저장소에 포함되지 않으므로 직접 준비합니다. 두 폰트가 **같은 구조**로 그리는 글자, 즉 부품과 배치가 일치하고 스타일만 다른 글자를 나열한 것입니다.

이 파일이 있으면 `prepare`가 글자마다 "참조의 구조 → 타깃의 자형" 학습 표본을 만듭니다. 모델이 실제 참조 폰트를 입력으로 보는 유일한 기회입니다. 없으면 타깃 자기재구성만 하게 되며, 실행은 되지만 생성 시 실제로 받게 될 입력을 모델이 학습 중에 한 번도 보지 못합니다.

구조가 다른 글자는 넣으면 **안 됩니다**. 그런 쌍은 한 지역 자형을 다른 지역 자형으로 바꾸도록 모델을 가르치는 것이며, 참조 폰트를 쓰는 목적과 반대입니다.

만드는 과정은 두 단계이고 그 사이에 눈으로 확인하는 일이 들어갑니다.

```bash
python tools/same_form_review.py render --screen   # 좌우 대조 이미지를 same_form_review/ 에 출력
# 좌우 구조가 다른 이미지를 삭제
python tools/same_form_review.py collect           # 남은 파일 이름으로 목록을 작성
```

`--screen`은 연결 성분 수, 구멍 수, 오일러 수가 이미 어긋나는 글자를 먼저 걸러냅니다. 첫 회차에는 쓸 만하지만 작업량을 줄이는 것이지 판정하는 것이 아닙니다. 위상 비교로는 일본 자형이나 잘못된 획 끝을 가려낼 수 없으므로 남은 글자는 한 글자씩 눈으로 확인해야 합니다. 형식은 [data/README.md](data/README.md)에 있습니다.

## 실행 환경

NVIDIA GPU가 필수입니다. CUDA 없이는 학습이 동작하지 않습니다.

| 환경 | 학습 |
|---|---|
| Windows / Linux + NVIDIA | 가능 |
| macOS | 불가. NVIDIA GPU가 없고 Apple MPS도 미지원 |
| 외장 GPU 없음 | 불가 |

Python 3.10-3.14, 여유 디스크 150 GB 권장. VRAM 12 GB면 충분하며 기본값이 여기에 맞춰져 있습니다.

Mac에서도 설치, 자체 점검, 폰트 검사, 이미 생성된 이미지를 폰트로 묶는 작업까지는 가능합니다. 학습은 NVIDIA 카드가 있는 기기에서 하십시오.

## 시작하기

### Windows

| 단계 | 더블클릭 | 내용 |
|---|---|---|
| 1 | `install.bat` | 환경 구축. 한 번만 |
| 2 | — | 폰트를 `fonts\`와 `refs\`에 넣기 |
| 3 | `verify.bat` | 확인 |
| 4 | `run.bat` | 실행 |

`stop.bat`으로 다음 체크포인트에서 안전하게 종료합니다. `run.bat`을 다시 실행하면 이어서 진행됩니다.

### Linux / macOS

```bash
./install.sh          # 환경 구축
./verify.sh           # 폰트를 둔 뒤 확인
./run.sh              # 실행. ./stop.sh 로 일시 정지
```

`Permission denied`가 나오면 먼저 `chmod +x *.sh`를 실행하십시오.

## VRAM 설정

기본 `config.json`은 12 GB에 맞춰져 있어 12 GB 카드라면 변경할 필요가 없습니다. 다음은 RTX 5070 Ti Laptop(11.9 GB)에서 측정한 1 스텝 최대 사용량입니다.

| 단계 | 기본 batch | 최대 VRAM |
|---|---|---|
| vq256 | 4 | 3.1 GB |
| vq384 | 2 | 3.4 GB |
| vq512 | 1 | 3.0 GB |
| direct256 | 6 | 4.6 GB |
| direct384 | 3 | 5.2 GB |
| latent256 | 6 | 5.4 GB |
| latent384 | 4 | 7.8 GB |
| latent512 | 4 | 11.2 GB |

### 권장값

| VRAM | 변경 내용 |
|---|---|
| 16 GB 이상 | 불필요 |
| 12 GB | 불필요 |
| 10 GB | `latent512`의 `batch_size` 4에서 2로, `gradient_accumulation` 1에서 2로 |
| 8 GB | 위에 더해 `latent384`도 4에서 2로 / 1에서 2로 |
| 6 GB | 모든 단계에서 `batch_size` 절반, `gradient_accumulation` 두 배 |

원칙은 `batch_size`와 `gradient_accumulation`의 곱을 유지하는 것입니다. 바뀌면 유효 배치가 달라져 학습률이 맞지 않게 됩니다.

VRAM이 많다고 크게 빨라지지는 않습니다. 병목은 메모리가 아니라 연산이며, batch를 4에서 8로 올려도 처리량 향상은 10% 미만이었습니다.

## CPU 설정

`training.workers`는 데이터 적재 프로세스 수이며 기본값은 4입니다.

| 물리 코어 | workers |
|---|---|
| 4 | 2 |
| 6-8 | 4 (기본) |
| 12 이상 | 6-8 |

worker 하나당 약 1.5-2 GB 메모리를 씁니다. 메모리가 빠듯하면 줄이십시오.

`cpu_threads`, `interop_threads`, `opencv_threads`는 올리지 마십시오. 학습은 GPU 위주이므로 이 값을 올리면 CPU가 GPU 스케줄링을 뺏을 뿐입니다.

worker를 늘릴지 판단하려면 실행 중 터미널의 batch/s를 보십시오. GPU 사용률(`nvidia-smi`)이 계속 80% 아래면 효과가 있고, 90% 이상이면 연산 제약이라 늘려도 달라지지 않습니다.

## 설정 변경

설정은 프로젝트 최상위의 `config.json`이며 네 개의 실행 스크립트가 넘기는 것도 이 파일 하나입니다. 저장은 UTF-8로 하십시오.

각 단계에는 `name`이 있으므로 이름으로 찾는 것이 확실합니다. 8 GB 카드라면 `fusion` → `diffusion` → `phases` 안의 `"name": "latent512"` 항목을 고칩니다.

```json
{
  "name": "latent512",
  "batch_size": 2,
  "gradient_accumulation": 2
}
```

곱은 여전히 4로 변하지 않습니다.

### 기존 진행이 무효가 되는 변경

체크포인트는 지문으로 대조합니다. 맞지 않으면 해당 단계의 1 에포크부터 다시 시작합니다.

| 변경 | 결과 |
|---|---|
| `fusion.vq.phases[]`의 어떤 항목이든 | 해당 VQ 단계 재학습 |
| `fusion.diffusion.phases[]`의 어떤 항목이든 | 해당 확산 단계 재학습 |
| `fusion.style_encoder`의 `size`, `epochs`, `batch_size`, `learning_rate`, `virtual_length`, `references_per_set`, `cell_grid`, `query_gain` | 스타일 단계 재학습 |
| `fusion.refiner`의 `size`, `epochs`, `batch_size`, `gradient_accumulation`, `learning_rate` | 정교화 단계 재학습 |
| `fusion.style_encoder.early_stopping` | 안전 |
| `fusion.refiner.minimum_epochs`, `minimum_relative_improvement` | 안전 |
| `training.workers`, `training.amp`, `checkpoint_every_steps`, `preview_every` | 안전 |
| `build`의 어떤 항목이든 | 안전. TTF 생성 시에만 읽습니다 |

VQ와 확산의 `early_stopping`은 phase 안쪽에 있어서, 고치면 해당 단계가 재학습됩니다. 스타일 단계, 정교화 단계와는 다른 점입니다.

VRAM 관련 설정은 실행 전에 정하십시오. 도중에 바꾸면 그 단계를 다시 해야 합니다.

### VRAM 부족

오류가 어느 단계에서 났는지 확인하고(터미널에 단계 이름이 표시됩니다) 그 단계만 고칩니다. `batch_size` 절반, `gradient_accumulation` 두 배, 그래도 부족하면 한 번 더.

### 폰트가 너무 큼

용량의 대부분은 자형 윤곽입니다. 이를 제어하는 것은 `build.curve_simplify`이며, 값이 클수록 남기는 점이 줄어듭니다. 참조 폰트에서 복잡도가 다른 17자를 측정한 결과입니다.

| `curve_simplify` | 점 수/자 | Dice |
|---|---|---|
| 0.55 | 611 | 0.9848 |
| 1.2 (기본) | 167 | 0.9843 |
| 1.8 | 130 | 0.9812 |
| 2.5 | 117 | 0.9786 |

수작업으로 설계된 폰트는 한 글자당 약 156점이므로 기본값이 그 수준입니다. 이만 자 남짓이면 약 14 MB가 됩니다. 1.8을 넘으면 일치도가 뚜렷하게 떨어집니다. 0.55까지 낮춰도 이점은 없으며, 늘어난 점은 자형이 아니라 래스터의 계단을 따라 그린 것입니다.

다른 조절값은 효과가 약합니다. `maximum_points_per_contour`를 480에서 96으로 낮춰도 69%까지만 줄었습니다. 건드릴 필요가 없습니다.

용량 내역을 보려면 다음을 실행합니다.

```bash
python tools/font_size_report.py build/target-HanziStyleForge.ttf
```

## 중단에 대하여

단계마다, 생성된 글자마다 체크포인트가 있으므로 같은 명령을 다시 실행하면 중단 지점부터 이어집니다. 정전, 블루스크린, Ctrl+C 모두 동일합니다. 실행 스크립트는 오류 후 자동으로 재시도하며 20회 연속 실패해야 멈춥니다.

실행 스크립트를 쓰지 않고 직접 명령을 입력해 재개할 때는 주의가 필요합니다. 정지를 요청하면 프로젝트 최상위에 `STOP_AFTER_CHECKPOINT` 표식이 남습니다. 실행 스크립트는 시작할 때마다 이를 지우지만 직접 입력한 명령은 지우지 않으므로, 새 실행이 첫 체크포인트에서 멈춥니다. 수동 재개 전에 삭제하십시오.

## 자주 묻는 질문

**얼마나 걸립니까.** 글자 수와 GPU에 따라 며칠에서 몇 주입니다. 기본 설정으로 12 GB 노트북 GPU라면 주 단위입니다.

**일부 글자만 생성할 수 있습니까.** 가능합니다. `scope.mode`를 `chars_file`로 하고 `scope.extra_chars_file`이 글자 목록(한 줄에 한 글자, 또는 `U+4E00` 형식의 코드포인트)을 가리키게 하십시오. 먼저 수백 자로 시험해 보는 것이 좋습니다.

**생성된 글자가 규범에서 벗어날 수 있습니까.** 구조 게이트가 있습니다. 연결 성분 수와 구멍 수가 참조 글자와 맞지 않는 후보는 거부되고 참조 자형이 대신 쓰입니다. 획이 하나 많거나 적은 오자는 막을 수 있지만, 일부 글자가 참조 폰트의 모습으로 남는 대가가 있습니다.

**한자가 아닌 내용도 바뀝니까.** 바뀌지 않습니다. 라틴 문자, 숫자, 문장 부호, 가나, 한글, 그리고 OpenType의 레이아웃과 힌팅 데이터는 모두 `target.ttf`에서 그대로 보존되며 빌드 시 바이트 단위로 검증됩니다.

**`requires CUDA, but torch.cuda.is_available() is False` 오류** 사용 가능한 NVIDIA GPU를 찾지 못했습니다. 드라이버를 갱신하거나 CUDA 버전 PyTorch가 설치되어 있는지 확인하십시오.

**`does not support training.device='mps'` 오류** Apple GPU는 지원하지 않습니다.

## 동작 원리

```text
target.ttf (스타일)  ref.otf (자형 구조)
        └──────┬──────┘
               ↓
   스타일 부호화 → VQ 획 코드북 → 잠재 확산 → 정교화
               ↓
   다중 후보 생성 → 구조 게이트 → 품질 검사 → 벡터화 → TTF
```

학습 표본은 두 종류입니다. 타깃 폰트의 자기재구성, 그리고 동일 자형 목록이 다루는 "참조의 구조 → 타깃의 자형" 쌍입니다. 둘 다 정답은 `target.ttf`에서만 가져오고, 구조 입력은 `target` 자신이나 `ref` 중 한쪽에서만 가져옵니다. 이 데이터 흐름은 실행 시 검증됩니다.
