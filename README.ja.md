# HanziStyleForge Fusion

**あるフォントのスタイルで、別のフォントの字形基準に従い、漢字をすべて生成し直します。**

対象フォントの筆画スタイルを学習し、参照フォントが収録する**すべて**の漢字を、その字形構造に沿って描き直して、そのままインストールできる `.ttf` にまとめます。

「不足分の補完」ではなく「生成し直し」である点にご注意ください。対象フォントに既にある字も参照側の字形で描き直します。そうすることで書体全体の統一が取れます。

代表的な使い方は 2 つあります。

- **収録字数を増やす。** 数千字しかない対象フォントを二万字規模へ
- **字形基準を変える。** 対象フォントが台湾（あるいは日本、韓国）の字形で、中国大陸の字形にしたい場合。参照フォントを大陸版に差し替えれば、スタイルはそのままに字形だけ新しい基準で描き直されます

> 実験的なツールです。一度の実行に数日から数週間かかります。いつ中断しても、次回は続きから再開します。

## 用意するフォントは 2 つ

| ファイル | 役割 | 内容 |
|---|---|---|
| `fonts/target.ttf` | **スタイル** | 好きなフォント。筆画の見た目だけを学習します |
| `refs/ref.otf` | **字形** | 字数の揃ったフォント。その字形構造に従います |

例：`target.ttf` に手書き風フォント、`refs/ref.otf` に源ノ角ゴシックを置くと、源ノ角ゴシックの字形で手書き風に描かれたフォントが得られます。

**字形の基準は `ref.otf` が決めます。** 中国大陸の字形が欲しければ大陸版の参照フォントを、台湾・香港・日本・韓国の字形が欲しければそれぞれのフォントを置いてください。プログラムがどれを「正しい」と判断することはありません。

### フォントファイルの条件

- 静的フォント。**可変フォント、TTC、OTC は非対応**
- `target.ttf` は TrueType（`glyf` テーブルを含むもの）
- `ref.otf` は TrueType でも CFF/OTF でも可

## 動作環境

**NVIDIA GPU が必須です。** 学習がこのプロジェクトの本体で、CUDA を必要とします。

| プラットフォーム | 学習の可否 |
|---|---|
| Windows + NVIDIA | 可 |
| Linux + NVIDIA | 可 |
| macOS | **不可**。Mac に NVIDIA GPU はなく、Apple の MPS も未対応です。CPU のみでは実用にならない速度になります |
| 独立 GPU のない Linux / Windows | 同上 |

そのほか：Python 3.10-3.14、空き容量 150 GB 以上を推奨。VRAM は 12 GB あれば十分で、同梱の設定はそれに合わせて調整されています。

Mac でもインストール、セルフテスト、フォントの確認、既にある字形画像からのフォント構築はできます。学習には NVIDIA GPU を積んだマシンをご用意ください。

## VRAM 別の推奨設定

同梱の `config_months_12gb.json` は **12 GB** に合わせてあります。12 GB のカードなら何も変更する必要はありません。

以下は RTX 5070 Ti Laptop（11.9 GB）で実測した 1 ステップのピーク VRAM です。推奨値はここから算出しています。

| ステージ | 解像度 | 1 サンプル追加あたり | 固定分 |
|---|---|---|---|
| VQ オートエンコーダ | 256 / 384 / 512 | 0.37 / 0.83 / 1.47 GB | 約 0.13 GB |
| 拡散（VQ・スタイルエンコーダ・EMA 込み） | 256 / 384 / 512 | 0.34 / 0.76 / 1.35 GB | 約 0.44 GB |
| リファイナ | 384 | 0.62 GB | 約 0.40 GB |

### 推奨値

変更が必要な箇所だけを挙げています。記載のない項目は既定のままにしてください。

| VRAM | 変更内容 |
|---|---|
| **8 GB** | `fusion.diffusion.phases[2]`（latent512）：`batch_size` 4 → **2**、`gradient_accumulation` 1 → **2** |
| **12 GB** | **変更不要。** これが既定値です |
| **16 GB 以上** | 累積を実バッチに畳み込みます：<br>`fusion.vq.phases[1]`（vq384）：バッチ 3 → **6**、累積 2 → **1**<br>`fusion.vq.phases[2]`（vq512）：バッチ 1 → **4**、累積 4 → **1**<br>`fusion.direct_baseline.phases[1]`：バッチ 3 → **6**、累積 2 → **1**<br>`fusion.refiner`：バッチ 2 → **4**、累積 2 → **1**<br>`fusion.purification`：バッチ 2 → **4**、累積 2 → **1** |

### 破ってはいけない唯一のルール

**`batch_size × gradient_accumulation` の積を変えないでください。**

この積が**実効バッチサイズ**であり、学習結果を決めます。VRAM が少なければ `batch_size` を半分に、`gradient_accumulation` を倍にします。勾配は同じで、何回に分けて貯めるかが違うだけです。積が変わると速度だけでなく学習そのものが変わり、学習率の再調整も必要になります。

### VRAM を増やしても大して速くなりません

このパイプラインは **VRAM ではなく演算律速**です。累積を畳み込んだ実測値は拡散で 1.06 倍、VQ で 1.12 倍にとどまりました。24 GB のカードと 16 GB のカードは同じ設定でほぼ同じ速度で動きます。実効バッチサイズを上げる（結果が変わります）か解像度を上げる以外に、余った VRAM の使い道がないからです。

**大きなカードに買い替えても、数週間が数日になることはありません。** 所要時間を決めるのは GPU の演算性能と文字数です。

## 設定ファイルの編集方法

### ファイルの場所

プロジェクト直下の **`config_months_12gb.json`** です。4 つの起動スクリプト（`run_months_resilient.bat`、`run.sh` など）はすべてこのファイルを渡すので、編集するのはこれだけです。

テキストエディタなら何でも構いません。**保存は UTF-8 で行ってください。**

### 該当箇所の探し方

設定は入れ子になっています。`fusion.vq.phases[2].batch_size` は上から順にたどります。

```json
{
  "fusion": {                    ← "fusion" を探す
    "vq": {                      ← その中の "vq"
      "phases": [                ← その中の "phases"（リスト）
        { "name": "vq256", ... },     ← [0] 1 番目
        { "name": "vq384", ... },     ← [1] 2 番目
        { "name": "vq512",            ← [2] 3 番目（0 から数える）
          "size": 512,
          "batch_size": 1,       ← ここ
          "gradient_accumulation": 4
        }
      ]
    }
  }
}
```

各フェーズには `name` があるので、名前で探すのが最も確実です。

### 実例：8 GB のカード

`fusion` → `diffusion` → `phases` の中から `"name": "latent512"` のブロックを探します。

```json
{
  "name": "latent512",
  "size": 512,
  "batch_size": 2,             ← 元は 4
  "gradient_accumulation": 2,  ← 元は 1
  ...他はそのまま
}
```

積は `4 × 1` から `2 × 2` になり、4 のまま変わりません。

### 編集前に：既存の進捗が破棄される条件

チェックポイントを再利用できるかは「フィンガープリント」で判定されます。一致しない場合、そのステージは**エポック 1 からやり直し**になり、学習済みの内容は破棄されます。

| 変更した項目 | 結果 |
|---|---|
| `fusion.vq.phases[]` 内の**いずれか** | その VQ フェーズが最初から再学習 |
| `fusion.diffusion.phases[]` 内の**いずれか** | その拡散フェーズが最初から再学習 |
| `fusion.style_encoder` の `size`、`epochs`、`batch_size`、`learning_rate`、`virtual_length`、`references_per_set`、`cell_grid`、`query_gain` | スタイルステージが最初から再学習 |
| `fusion.refiner` の `size`、`epochs`、`batch_size`、`gradient_accumulation`、`learning_rate` | リファイナが最初から再学習 |
| `fusion.style_encoder.early_stopping` 以下のすべて | **安全**。次のエポックから反映 |
| `fusion.refiner.minimum_epochs`、`minimum_relative_improvement` | **安全** |
| `training.workers`、`training.amp`、各 `checkpoint_every_steps`、`preview_every` | **安全** |

**陥りやすい罠：** VQ と拡散では `early_stopping` がフェーズの*内側*にあるため、これを変更しても該当フェーズが再学習になります。スタイルステージとリファイナは異なります。

したがって **VRAM 関連の設定は開始前に決めてください。** 途中でメモリ不足に気づいて修正すると、そのステージをやり直すことになります。

### メモリ不足になったら

`CUDA out of memory` にはどのステージで起きたかが示されます（ターミナルに `vq512`、`latent384` などのフェーズ名が出ます）。手順は次のとおりです。

1. そのフェーズの `batch_size` を半分にする
2. 同じブロックの `gradient_accumulation` を倍にする
3. まだ落ちるなら繰り返す

失敗したフェーズだけを変更してください。まとめて変更しないこと。

### 壊していないかの確認

```bash
./verify.sh
```

Windows では `verify_project.bat` をダブルクリックします。JSON の構文と値の範囲を検査します。JSON で最も多い誤りは**カンマの過不足**です。ブロック内の最後の項目にカンマを付けてはいけません。

## 使い方

### Windows

次の 4 つを順にダブルクリックします。

| 手順 | ダブルクリック | 内容 |
|---|---|---|
| 1 | `install_cuda130.bat` | 環境構築。初回のみ |
| 2 | — | 2 つのフォントを `fonts\` と `refs\` に置く |
| 3 | `verify_project.bat` | 準備が整っているか確認 |
| 4 | `run_months_resilient.bat` | 実行開始 |

中断したいときは `request_safe_stop.bat` をダブルクリックすると、次のチェックポイントで安全に終了します。`run_months_resilient.bat` をもう一度ダブルクリックすれば続きから再開します。

### Linux と macOS

プロジェクトのフォルダーでターミナルを開きます。

```bash
./install.sh
```

2 つのフォントを `fonts/` と `refs/` に置いてから：

```bash
./verify.sh
./run.sh
```

中断したいとき：

```bash
./stop.sh
```

`./run.sh` をもう一度実行すればチェックポイントから再開します。

> `Permission denied` と出る場合は先に `chmod +x *.sh` を実行してください。

## 中断したらどうなるか

問題ありません。各段階と生成済みの各字がチェックポイントとして保存されており、同じコマンドをもう一度実行すれば止まった所から続きます。

停電、クラッシュ、Ctrl+C のいずれでも同じです。`run_months_resilient.bat` と `run.sh` はエラー後に自動で再試行し、20 回連続で失敗した場合にのみ停止します。そこまで続けば一時的な不調ではなく本当の不具合だからです。

## よくある質問

**どのくらい時間がかかりますか。**
字数と GPU 次第で数日から数週間です。12 GB のノート PC 用 GPU で同梱設定なら、週単位で見込んでください。

**一部の字だけ処理できますか。**
できます。設定の `scope.mode` を `chars_file` にし、`scope.extra_chars_file` で 1 行 1 字（または `U+4E00` 形式）のリストを指定します。まず数百字で試すのがおすすめです。

**字形の基準から外れた字が出ませんか。**
構造ゲートがあります。生成した字の連結成分数や穴の数が参照と食い違う場合は却下し、参照字形を使います。画数が増減した誤字は防げますが、その代わり一部の字は目標のスタイルではなく参照側の見た目のままになります。

**漢字以外は変更されますか。**
されません。ラテン文字、数字、約物、仮名、ハングル、および OpenType のレイアウト・ヒンティングのテーブルは `target.ttf` からそのまま引き継がれ、ビルド時にバイト単位で検証されます。

**`requires CUDA, but torch.cuda.is_available() is False` と出ます。**
使用可能な NVIDIA GPU が見つかりません。ドライバーを更新するか、CUDA 版の PyTorch が入っているか確認してください。

**`does not support training.device='mps'` と出ます。**
Apple GPU は非対応です。上の動作環境をご覧ください。

## 仕組み

```text
target.ttf（スタイル）  ref.otf（字形構造）
        └──────┬──────┘
               ↓
   スタイル符号化 → VQ 筆画コードブック → 潜在拡散 → 精緻化
               ↓
   複数候補 → 構造ゲート → QA → 輪郭ベクトル化 → TTF
```

スタイルは `target.ttf` からのみ、構造は `ref.otf` からのみ取り込みます。2 つのデータ経路は分離されており、その分離は実行時に検証されます。
